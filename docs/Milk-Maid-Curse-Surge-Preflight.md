# Milk Maid curse surge preflight

Prepared 2026-10-27. Audit only: no gameplay, package, installed-mod, profile, or game changes.

## Intended behavior

Keep the chest curse relevant after nearby eligible characters have become Milk Maids. Prefer an eligible allied female non-Milk Maid for the existing conversion. When none exists, select an eligible existing Milk Maid under the same player/nearby-allies scope and apply a milk surge instead. Do not redirect an ordinary busy conversion failure into a surge against another actor.

Add a percentage slider, proposed range 0–100%, steps of 5%, default 50%. Zero disables the existing-maid surge only; it does not disable conversion. Calculate the addition from the target's maximum, not current milk or remaining space: current 8 / max 10 at 50% becomes 13 / 10. No Lactacid, level, slot, capacity, inventory, or conversion-history changes on a surge.

One random story from the user's five new curse variations applies to either successful chest outcome. Replace blank name positions with {actor}. Existing-maid text must never claim a new conversion. Reuse the current brief conversion/curse notifications, with their existing toggles, for both outcomes. Keep player story popups player-only by default and honor the existing story toggle. NPCs receive animation and configured notification/narration, not an extra blocking message box.

Suppress the generic forced-conversion opening and closing story only for the chest curse; show one new curse story instead. Other conversion callers retain their present stories and behavior. Avoid two narrations describing one outcome; distinguish curse presentation from authoritative MilkmaidCreated publication, which belongs to successful conversion only.

## Verified source evidence

- MMEDungeonChestConversion.HandleActivation currently selects mode 2, which excludes existing maids, before chance. Chest state uses resolved/pending keys. A successful conversion resolves the chest and returns 1. A failed chance resolves it; temporary failures clear pending and allow retry.
- MMEAlertsController invokes armor trap first, then conversion, then MMEChestMilkTrap if conversion did not complete. Surge success must return 1 from the same curse branch. Armor priority stays unchanged.
- MMEChestTrapTargets is a bounded same-cell allied-female scan, radius 1500, with player-only configuration support. Add an explicit existing-maid mode that reuses the Milk Maid curse scope toggle; do not change armor/drink targeting or silently broaden to strangers/males/children.
- Original installed MME_Storage declares changeMilkCurrent(Actor akActor, Float Delta, Bool enforceMaxValue). False bypasses the maximum for that write. getMilkMaximum(Actor) returns the stored capacity, lazily initializing it when missing. Original MilkQUEST later clamps/leaks excess in its ordinary cycle, including when BreastScaleLimit is enabled. Preserve that subsequent framework behavior; do not promise permanent overflow.
- MMEMilkBoost currently mirrors BreastScaleLimit. Do not reuse its drink-specific bonuses or pending player-drink markers for this curse. Apply the exact percentage through MME's own change function, refresh CurrentSize, then reconcile existing body/fullness/armor systems through their appropriate non-drink route. Verify which reactions are deferred until animation ownership releases; avoid launching a second reaction during the curse.
- TryCreateMilkMaidForcedAnimated already owns registration, Lactacid initialization, the ZaZAPCHorFd performance, and generic player stories. It deliberately rejects existing maids. Calling it for a surge would be incorrect.
- MMEReactionAnimation.StartPresentationKneeling already supports presentation without Milk Maid membership and owns cooperative animation/movement locks. Reset/UnlockMovement avoid resetting an external scene, and RestorePlayerMovementIfNeeded recovers interrupted player/NPC movement before the controller master-toggle early return. Reuse this mechanism instead of a second raw SetDontMove implementation.
- Existing forced conversion directly uses SetUnconscious and broad Disable/EnablePlayerControls. A shared reaction should not blindly inherit those broad resets. Preserve other mods' state; movement ownership is separate from animation ownership. Do not reacquire the same actor via a helper after the conversion already owns its animation lock.

## API / implementation design

1. Provide a public conversion-free New Milk Maid reaction API, backed by a narrow presentation service. It performs the established kneeling event and moan for roughly ten seconds, holds the actor's movement, and cleans up its own ownership only. It does not assign slots, alter milk/Lactacid, emit conversion events, or choose stories. Guard enabled state, actor lifecycle/adulthood, combat/mount/sit, optional scene owners, restraints, and existing animation ownership. Clearly document that SendAnimationEvent does not confirm graph playback; API results describe dispatch/cleanup, not proof of visual animation.
2. Keep the existing public TryCreateMilkMaidForcedAnimated signature and default behavior. Add an explicit context-aware/internal path for chest conversion that suppresses generic stories and delegates the shared performance exactly once. Keep registration and original postconditions in MMENewMilkMaid. Account for its existing global conversion lease and actor lock; do not let presentation reset or release another owner's lock. Limit refactoring to necessary shared performance, cleanup, and story context.
3. Implement a small curse service or facade for the existing-maid surge, with a documented success/commit contract. Revalidate membership and capacity immediately before the write. Reject invalid/nonpositive/nonfinite capacity or requested amount. Obtain the actor's action/presentation ownership before changing milk, snapshot current/max, write the uncapped delta once, read back, and distinguish accepted gameplay from later presentation interruption. Once milk was added, retain the chest's committed state even if a later animation step fails. Do not refund by writing an old total over concurrent MME production or allow a chest retry to duplicate committed milk.
4. Maintain the existing chance roll, chest identity, pending protection, and armor/curse/drink priority. A completed surge and conversion each consume that chest once. Failed chance remains resolved. Disabled surge, absent targets and temporary state rejection are ordinary skips. Resolved old chests remain resolved; previously unresolved chests may now surge. Give pending action/load recovery an explicit policy so interrupted latent work cannot strand a chest or apply the same milk twice. Existing global pending keys have no timestamp: do not assume they expire automatically.
5. Store five new random stories as a new JSON string list, preferably alongside existing ForcedMilkMaidConversion configuration, preserving openingStory, closingStory and conversionMessages for current callers. Provide safe fallback if the pool is empty/malformed; sample once per event and log only the selected index. Preserve editable player wording and avoid introducing an optional dependency. Random selection may repeat; immediate-repeat prevention is optional, not part of required scope.
6. Add MCM option/reset/slider handlers and HasValue-guarded migration preserving existing settings. Advance internal MCM/API capability revisions only as needed, not user release numbers. Update help to explain additional milk, overflow and zero behavior. No new ESP records are required unless implementation discovers a concrete need.

## Diagnostics and smoke alarms

Use MMELog.MasterDiagnostic for sparse entry, chest identity/kind, scope/selected actor identity, membership, conversion versus surge, chance result, maximum/percentage/requested delta, before/after/actual delta, selected story index, animation/movement lock acquisition, skip reason and cleanup/commit. Do not require verbose logging for these footprints or put routine diagnostics in notifications.

Deduplicate/rate-limit alarms for malformed activation, missing required MME/controller, invalid registered-maid capacity, failed storage postconditions, broken lock recovery or impossible state. Disabled feature, chance miss, no target, cooldown, active scene, restrained actor and already-maid membership are expected skips. A surge selecting an existing maid is normal, not an alarm.

## Build and regression plan

- Player conversion and NPC conversion: registration exactly once; existing MME faction, slots, level and Lactacid initialization preserved. One chest story, no generic duplicate popup or creation narration.
- Player surge and NPC surge: 0/current/full/already-overfull state; 5/50/100% and zero-disabled; max-based addition, actual overflow, no conversion or Lactacid change. Verify later native MME clamp/leak behavior rather than changing it.
- Mixed party prioritizes conversion; all-maid party surges. Player-only toggle, distance/cell, female/adult/allied/hostility guards; membership changes during dispatch; missing optional dependencies.
- Same chest reopened during/after request, chance miss, failed precommit animation eligibility, postcommit interruption, simultaneous chests, stale pending and existing-save/load recovery. No duplicate milk and no permanently locked actors/chests.
- Combat, mount, sitting, restraint, SexLab/OStim/MME scene takeover, death/unload, master disabled mid-sequence, save/load during hold, existing SetDontMove/unconscious/control state. No unconditional foreign animation/control reset. Verify animation and movement independently.
- Notifications/narration/story toggles independently, new pool valid/empty/missing, {actor} Unicode names and escaping, exactly one random popup for the player, no NPC popup interruption. Do not route long stories into duplicate automatic TTS/narration by accident.
- Compile every changed PSC. MMENewMilkMaid is generated into the OStim-only backend: regenerate and compile affected variants, keeping new presentation code dependency-neutral and checking effective bytecode for SexLab references. Existing compatibility/conversion/array-cast contracts remain applicable.
- Rebuild MME Extensions.zip and inspect matching PSC/PEX, JSON/FOMOD contents, both backend choices and MO2/Vortex XML. Keep build diagnostics out of ZIP. Do not install, deploy, launch, sort, or change profiles as part of implementation without explicit authorization.

## Decision

Ready for implementation with these boundaries. Main risks are conversion-lock interaction during extraction, duplicate application after a postcommit failure, and movement/control cleanup on interrupted saves. Prefer the existing presentation/movement machinery and a narrow context-aware conversion path. Live acceptance must verify both actor routes and overflow lifecycle; static compilation alone cannot establish animation playback or cleanup under every external mod.
